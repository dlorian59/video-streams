# Video Streams 0.1.0 — от загруженного ролика к просмотру

[README](../../README.md) · [Versions / Версии](../index.md) · [English](en.md) · [Русский](ru.md) · [API](reference.ru.md)

## Один ролик, три разных результата

Успешная загрузка файла означает, что оригинальный объект сохранён. Готовое видео означает, что записаны медиасегменты и итоговый плейлист. Воспроизведение означает, что браузер получил достаточно данных и декодировал их. Разделяйте эти состояния в UI: загрузка → подготовка → готовность → просмотр. Ошибка подготовки не отменяет сохранённый источник, а ошибка декодирования не означает сбой загрузки.

Дополнение предназначено для записанных коротких видео, хранилище и авторизация которых уже принадлежат приложению. V1 — подготовка видео по запросу с фиксированным качеством. Прямому эфиру, шифрованному входу, нескольким качествам и долговечной очереди обработки нужен другой контракт; пакет не имитирует эти возможности.

```text
committed source object → prepare → immutable HLS generation → browser session
```

Обычная загрузка/скачивание через file-streams остаётся одним потоком. Сегменты HLS — отдельное представление для просмотра, не прикладная нарезка загрузки оригинала.

## 1. Переиспользовать хранилище и подготовить источник

Возьмите Java-зависимость из README. Core принимает существующий ObjectStreams и приватный каталог с правом записи. Нужны Java 17+, рабочая файловая система с POSIX permissions и внешние ffmpeg/ffprobe с поддержкой libx264/AAC. Библиотека не скачивает исполняемые файлы и не создаёт хранилище.

```java
var options = VideoOptions.defaults(privateWorkDirectory);
var videos = new VideoStreams(applicationStorage, options);
Mono<VideoAsset> result = videos.prepare(authorizedSourceKey);
```

Создайте сервис один раз и закройте при остановке хоста. Mono — результат подготовки, не ID сохранённой задачи; верните его из WebFlux-сервиса либо подпишитесь в своём worker. Не закрывайте VideoStreams сразу после создания Mono без подписки. Полная реализация: [PrepareVideo.java](../../examples/java/PrepareVideo.java).

Хост сначала проверяет доступ к ключу и сохраняет источник неизменным во время подготовки. Повтор prepare создаёт другую генерацию, а не дедуплицирует операцию. Автоматического повтора и долговечной очереди нет. Если приложению нужна очередь, вызывайте тот же метод из существующего обработчика задач и сохраняйте полученную генерацию.

VideoAsset содержит generation, sourceKey, playlistKey, mimeType, durationSeconds и segmentCount. playlistKey — ключ хранилища, не публичный URL. URL с проверкой доступа создаёт хост после успешной подготовки.

## 2. Доставить файлы через существующую авторизацию

VideoAssetHandler переиспользует HTTP-адаптер file-streams. Ваш маршрут проверяет личность и доступ к источнику при каждом GET до делегирования:

```java
return assetHandler.handle(exchange, authorizedSourceKey, generation, name);
```

Handler принимает только playlist.m3u8, init.mp4 и segment-NNNNNN.m4s внутри вычисленного пространства генерации. Поддерживается только GET; знание UUID не даёт права доступа. Проверка только sourceKey открывает и исторические генерации, если приложение отдельно не ограничивает допустимые поколения.

| Маршрут полного примера | Назначение |
|---|---|
| PUT /api/video-sources/{id} | Существующая потоковая загрузка; дождитесь committed=true и сохраните key. |
| POST /api/videos/{id}/prepare | Тело {"sourceKey":"id"}; ждёт готовности и отвечает 201, не 202. |
| GET /api/videos/{id}/assets/{generation}/{name} | Повторно проверяет права на плейлист/init/сегмент. |

```json
{
  "status": "ready",
  "generation": "2a15bb1b-f405-46a2-b23f-a5102ed4a541",
  "playlistUrl": "/api/videos/demo%3Aclip/assets/2a15bb1b-f405-46a2-b23f-a5102ed4a541/playlist.m3u8",
  "durationSeconds": 12.0,
  "segmentCount": 6
}
```

JSON показывает форму ответа, не измеренный результат. Защищённый пример использует id=account:source, и key результата загрузки совпадает с id. Правило префикса аккаунта — пример: замените его сохранёнными ACL приложения. Сохраните CSRF для upload/prepare с cookie-сессией. Ссылки в плейлисте — относительные имена без реквизитов.

## 3. Подключить браузерную сессию

Добавьте @59alex/video-streams в package manifest по README. Полный [player.ts](../../examples/browser/player.ts) использует существующую сессию и CSRF-поля, ожидает подготовку и подключает воспроизведение. Возвращаются готовый asset и VideoSession без автоматического старта.

```ts
const controller = new AbortController();
const { session } = await prepareAndAttach(video, sourceKey, identity, controller.signal, showState);
```

Фрагмент вызывает экспортированную функцию полного примера; identity содержит scope, csrfHeader и csrfToken приложения. Библиотека не создаёт реквизиты. scope обозначает текущий аккаунт/сессию для transport hooks; это не токен и не ACL сервера. При смене аккаунта завершайте старую сессию.

```ts
await session.play();
session.pause();
session.seek(30);
session.dispose();
controller.abort();
```

Вызывайте play по действию пользователя и показывайте понятный UI при отклонении Promise. Строки выше — отдельные действия, не последовательность для немедленного запуска. dispose идемпотентен и прекращает свои запросы/слушатели/ресурсы плеера. Подключение к занятому video-элементу заменяет старую сессию. Вызывайте dispose/abort при уходе, смене источника и выходе из аккаунта. Не повторяйте upload/prepare автоматически после неизвестного результата.

onState/subscribe сообщают loading, ready, playing, paused, buffering, ended, error и disposed со временем, длительностью, буфером и счётчиками байтов/сегментов. Подготовка — отдельный Promise; фазы плеера не подтверждают загрузку источника.

## 4. Использовать полную связку Spring + React

Для Boot используйте отдельный стартер вместо ручного создания lifecycle beans процесса/хранилища. Он переиспользует file-streams, настраивает VideoStreams и VideoAssetHandler и не устанавливает публичных маршрутов.

```xml
<dependency>
  <groupId>io.github.59alex</groupId>
  <artifactId>video-streams-spring-boot-starter</artifactId>
  <version>0.1.0</version>
</dependency>
```

```yaml
file-streams:
  enabled: true
  http:
    enabled: false
  limits:
    profile: MEDIA
video-streams:
  enabled: true
  work-directory: ${VIDEO_WORK_DIRECTORY}
```

Сохраните настроенный storage client, реквизиты бакета и существующую защиту. Фрагмент отключает общие публичные файловые маршруты; контроллер проверяет права до делегирования. Полный пример также настраивает HTTPS и HttpOnly cookie-сессию. Не переносите демонстрационный вход в production-аутентификацию.

```text
video-streams-spring-boot-starter/examples/secured-video/
  src/main/java/example/video/
    VideoController.java   # authorization and HTTP routes
    VideoService.java      # ready response after prepare
    DemoSecurity.java      # example-only session/CSRF policy
    SessionController.java # session/CSRF information
  src/main/resources/application.yml
video-streams/examples/browser/player.ts
video-streams-react/examples/spring-react/VideoMessage.tsx
```

Полные комментированные исходники и разборы:

- [Spring service/controller and consumer](https://github.com/dlorian59/video-streams-spring-boot-starter/tree/main/examples/secured-video)
- [Starter README](https://github.com/dlorian59/video-streams-spring-boot-starter)
- [React attachment/player](https://github.com/dlorian59/video-streams-react)
- [Spring/React browser example](https://github.com/dlorian59/video-streams-react/tree/main/examples/spring-react)

Это адреса будущей публикации. До публикации репозиториев и пакетов используйте соответствующие соседние локальные копии и CONTRIBUTING. Наличие ссылок не означает, что GitHub или реестр уже предоставляют содержимое.

## 5. Выбрать бюджет ресурсов до приёма работы

VideoOptions.defaults требует рабочий каталог и задаёт срок 3 минуты, 512 МиБ входа, 512 МиБ выхода, 300 сегментов и 2 параллельные подготовки. Приём ограничен; BUSY — отказ при перегрузке, не неограниченная очередь ожидания. При цели 2 секунды стандартный бюджет сегментов также ограничивает входную длительность 600 секундами. Длинный или высокобитрейтный источник может раньше упереться в размер/время.

Вход скачивается в приватный временный файл: подготовка использует диск, не собирая весь источник в heap JVM. Выходной набор контролируется и проверяется до публикации. Проверки размера выполняются каждые 100 мс и допускают превышение между наблюдениями и не заменяют квоту ОС. Выделяйте диск под параллельные входы/выходы и накладные расходы; используйте изоляцию CPU/памяти/диска хоста и обновлённый FFmpeg для недоверенных медиа.

Браузерный предпросмотр нацелен на 4 секунды вперёд; при просмотре preview задаёт 12 секунд вперёд и 8 назад, playback — 24/12. Это цели буферизации hls.js. Один фрагмент, декодер браузера, буферы запросов и сохранённые медиа могут увеличить фактическую память. Жёсткий предел всей памяти браузера не гарантируется.

Loader ограничивает каждый ответ медиа 16 МиБ, плейлист 1 МиБ, запрещает redirects и ограничивает время запроса. preload:none всё равно получает плейлист, но откладывает медиа до запуска. Автоматических сетевых повторов, общего постоянного кэша и native-HLS fallback нет.

## 6. Границы кодеков и формата

Принимаются MP4/MOV с сигнатурой ftyp и Matroska/WebM с конечной положительной длительностью и видеопотоком. Размеры кадра ограничены; audio-only, плейлисты/URL, шифрованные медиа и неподдерживаемые сигнатуры отклоняются. Успех probe не обещает декодирование любого повреждённого файла.

Фиксированный профиль выбирает первый видеопоток и необязательный первый аудиопоток, сохраняет пропорции в пределах 1280×720 без увеличения, создаёт yuv420p H.264 High 3.1 при 30 fps и AAC 128 кбит/с при наличии аудио. Все дорожки, HDR-семантика, субтитры и главы не сохраняются. Ключевые кадры поддерживают примерно двухсекундные fMP4-сегменты HLS; последний может быть короче.

Результат — media playlist с init.mp4 и относительными именами, не master playlist и не набор ABR. Базовые механизмы описаны в [FFmpeg HLS muxer](https://www.ffmpeg.org/ffmpeg-formats.html#hls) и [hls.js compatibility](https://github.com/video-dev/hls.js#compatibility). Необходима поддержка MSE/кодеков браузером. Сам формат HLS не гарантирует декодирование профиля всеми браузерами.

## 7. Отмена, публикация и восстановление

Подготовка сначала публикует init/медиа, затем плейлист. До фиксации последнего плейлиста генерацию не следует предлагать пользователю. Сетевой сбой или отмена во время финальной загрузки могут оставить неизвестный результат: объект мог сохраниться без ответа ready.

В ObjectStreams нет API удаления. Ошибка может оставить неиспользуемые неизменяемые части; используйте политику хранения/очистки приложения. Не считайте отмену откатом загрузок, удалением оригинала или возможно сохранённого плейлиста. Сохраняйте успешный VideoAsset на сервере до ответа ready, если нужно восстановиться после потери HTTP-ответа или ограничить исторический доступ. При неопределённости самой публикации хранилища вызов может не вернуть asset/generation; endpoint поиска такой генерации в библиотеке нет. Разбор требует политики вашего хранилища/приложения.

Браузерный prepareVideo отличает явный отказ от неизвестного результата. Неизвестный результат нужно показывать как неопределённый, не как гарантированный провал с автоматическим повтором. Решение о восстановлении принимайте по состоянию приложения; скрытого polling/status endpoint в библиотеке нет.

## Что нужно знать

Хранилище владеет оригиналом, подготовка — временной работой и одной генерацией, браузер — одной сессией просмотра. Проверяйте каждый запрос файла, сохраняйте ID источника, сообщайте ready только после плейлиста и отличайте лимиты байтов от гарантий ресурсов хоста/браузера. API убирает медиаобвязку, не скрывая права, сохранение состояния и неопределённые результаты.
